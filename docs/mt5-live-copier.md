# MT5 Server API 同服跟单规格

状态：已取得用户提供的 SDK，开发基准为 Server API 6182。已实现业务核心、配置解析、原生 Windows 离线编辑器源码，并提供只读 SDK 探针工程。用户截图确认 VS2026 构建及两组测试通过；真实跟单执行、界面试用和测试服务器加载尚未完成，接入证据见 [SDK 核对结果](sdk-integration-notes.md)。

## 1. 当前范围

| 项目 | 已确认要求 |
| --- | --- |
| 执行端 | MT5 Server API C++ DLL，在 MT5 服务端执行 |
| 操作界面 | 独立 Windows 管理界面；不要求嵌入 Administrator |
| 服务器与账户 | 同一 MT5 Live；所有账户 Hedging、USD |
| 跟单关系 | 多对多；每条源账户到目标账户的关系独立配置 |
| 启用边界 | 仅该关系启用后新开的源交易，不补已有仓位 |
| 开仓方向 | 与源交易同方向 |
| 开仓手数 | 倍率、跟单提交前查询的净值比例、固定手数三种模式 |
| 平仓 | 同步源实际全部平仓和部分平仓 |
| 挂单 | 不复制；源成交建立新仓后才按新仓规则处理 |
| SL/TP | 不复制、不设置；源实际平仓结果仍同步 |
| 人工完全平仓 | 对应跟单仓位终止管理，不补仓、不再操作 |

MT4、Manager SDK、Netting、跨币种、跨服务器、跨平台、历史订单迁移均不属于当前实现范围。账户模式和币种仍应在执行前校验，不能只相信配置声明。

## 2. 多对多关系与仓位归属

每一条关系含稳定的 `relationship_id`、`source_login`、`follower_login`、启用状态、手数模式和参数。关系 ID 使用正的十进制数字字符串，适配到核心 `uint64` 时校验范围，不使用浮点数转换。例：A → X 使用 0.5 倍，A → Y 使用净值比例，B → X 使用固定 0.20 手；A → X 和 B → X 必须分别管理，不能合并为 X 的总仓位。

- 每条关系的启用基线、配置版本和手数参数相互独立。
- 拒绝同一源目标对重复配置、自跟随和整个关系图中的循环；允许同一目标接收多个源。
- 每个实际目标仓位只能归属明确的源交易与关系。关联键至少包括服务器身份、关系 ID、源账号、源持仓生命周期标识、目标账号和目标实际仓位标识。
- Hedging 下，同品种多个仓位分别关联；不能仅按品种、方向、订单备注或账户总手数平仓。
- 当前实现假设：插件自己生成的跟单交易不再次作为下一级开仓信号，防止多级关系产生意外级联。关系图校验仍独立执行。
- 同一关系同一动作只能有一个有效执行者，阻止重载或双实例造成重复交易。

## 3. 开仓手数计算

`S` 表示新源交易的实际开仓手数，`E_source`、`E_target` 表示收到源开仓成交后、在提交该次跟单前查询并冻结的双方 USD 净值。用户已确认这一采样时点；每条关系独立计算。

| 模式 | 目标理论开仓手数 | 对应配置参数 |
| --- | --- | --- |
| `multiplier` | `S × multiplier` | 正 decimal 字符串 `multiplier` |
| `equity_ratio` | `S × E_target / E_source × coefficient` | 正 decimal 字符串 `coefficient` |
| `fixed_lots` | 每个新源交易对应固定手数 | 正 decimal 字符串 `lots_per_source_trade` |

例：源开 1.00 手；倍率 0.50 对应 0.50 手；源净值 10,000 USD、目标净值 5,000 USD、系数 1.00 对应 0.50 手；固定手数 0.20 对应 0.20 手。

数量规则：

1. 金额、手数与系数在配置中使用十进制字符串；计算层应保证十进制规则和数量边界可审查，不以字符串表示替代 SDK 数量单位校验。
2. 开仓时冻结该交易所用的模式、参数及净值样本，之后改配置不追溯调整已有跟单仓位；目标净值变化也不触发已有仓位再平衡。
3. 净值比例在收到源开仓成交后，由独立工作线程在跟单提交前查询双方当前净值并冻结；同时记录源成交时间、源净值查询时间和目标净值查询时间。双方净值必须有效、为正且满足接入时确定的时效规则；失败时停止该次净值模式开仓，不以旧缓存替代。两次查询不保证原子同一时点，也不宣称重建了源成交瞬间净值。恢复时不能用当时净值补算漏单。领域核心中的整数货币单位不等于 SDK 原始净值精度，适配时应保留实际精度，不能预设最多两位小数。
4. 源、目标使用相同可交易品种及可比合约条件；按目标品种的最小手数、最大手数与步长校验。当前实现假设：向下对齐步长，不足最小手数跳过并记录原因，超出单次允许范围停止该次开仓并提示，不自动放大或拆成多单。
5. “每个新源交易”在本规格中指新纳入的 Hedging 持仓生命周期，不能将重复通知或同一开仓订单的分批成交各算一笔固定手数。固定模式只建立一次对应目标额度；倍率和净值模式按同一源交易累计实际开仓量核算，防止重复执行。
6. 同一源交易分批成交期间的后续开仓量与平仓交错，需要事件和数量账本支持；其识别、顺序及最终成交状态由 SDK 验证，不能仅按首条通知推断全部成交。

## 4. 部分平仓与目标实际余量

固定模式的比例规则已由用户明确；其他两种模式当前默认统一采用以下部分平仓规则：

```text
源平仓比例 = 本次源实际关闭数量 / 本次平仓前源实际剩余数量
目标理论关闭数量 = 该关系目标实际剩余数量 × 源平仓比例
```

例如源剩余 1.00 手，本次关闭 0.25 手；固定模式目标对应仓位实际剩余 0.20 手，则目标关闭 0.05 手、剩余 0.15 手。若公式产生 0.025 手等不符合目标步长的数量，实际执行需先按品种规则处理。

- 必须使用本次平仓前的源实际余量，以及执行前该跟单关系的目标实际余量，不能始终用最初开仓手数。
- 每次源关闭事件只处理一次，按关系与源仓位序列化；拒绝源剩余量非正、本次关闭量超出源剩余量等不一致状态。
- 当前实现假设：部分平仓数量向下对齐目标步长；小于最小可执行关闭量时不提交，记录差额。每次后续平仓重新依据实际余量计算；源完全平仓时关闭该关系的全部实际剩余量，避免永久留下尾仓。
- 若部分关闭会留下不合法的目标剩余量，暂停该次动作并提示，不能未经规则授权多平或超额平仓。
- 目标实际成交不足或交易结果未知时，以核对后的真实结果更新数量，不把提交数量视作已经成交。
- 源因手动操作、SL/TP、强平等原因实际减仓或平仓，均按确认后的关闭数量同步；不同原因及 Close By 的事件解释须由 SDK 验证。

## 5. 人工干预、挂单与 SL/TP

**目标手动全部平仓：** 对应映射进入终止状态。后续源减仓、平仓或事件重放均不再操作该目标映射，也不补仓；其他源交易和其他关系继续独立运行。

**目标手动部分平仓：** 当前实现假设为记录实际剩余量，之后源部分平仓继续按第 4 节的比例规则处理；不把被手动关闭的数量补回。只修改该仓位的数量账本，不影响同目标账户下其他关系。

**挂单：** 不在目标端创建、修改或删除源挂单的副本。无论源挂单是在关系启用前还是启用后放置，只要其成交后建立的是该关系启用后的新源仓位，就按新仓规则评估，且只跟一次。

**SL/TP：** 插件不复制或设置目标 SL/TP，也不因源 SL/TP 改动提交目标改单。源 SL/TP 触发并实际平仓后，按源平仓同步。当前实现假设：目标人工自行设置的 SL/TP 不由插件清除或改写；其触发后的实际余量与终止状态按人工干预原则核对。

## 6. 每条关系的“只跟新仓”边界

- 首次启用每条关系时，建立该源账号的已有仓位基线和可记录的启用边界。后添加目标或新添源目标关系不能继承其他关系的时间。
- 启用前已有仓位整体排除，包括之后的数量变化、减仓和关闭；同品种启用后建立的独立 Hedging 新仓可纳入。
- 不能仅凭事件收到的时间、未知 ticket 或 ticket 数值增大判断新仓。持仓 ticket 与生命周期标识的实际对应字段，须核对 Server API。
- 事件订阅和基线快照间的竞态需要补查与核对。无法确立可靠边界时，关系停留在待核对状态，不能猜测开仓。
- 插件重载或服务端重启沿用持久化基线和映射，不将恢复当作首次启用。
- 当前实现假设：暂停只停止该关系接纳新仓，继续管理已经跟随的仓位；恢复接纳时不追补暂停期间新仓。删除仍有在管仓位的关系应先转为暂停，保留其映射直到生命周期结束。
- 运行中断后先恢复已建立映射的真实状态；尚未跟到目标的漏接开仓不盲目追单，应显示待核对状态。离线追单的时间和价格边界不属于本阶段承诺。

## 7. 平台实现与独立界面

执行 DLL 承担源事件处理、关系筛选、开平仓提交、成交核对及状态持久化；Windows 界面承担关系编辑、逻辑校验、启停、状态和日志展示。界面原型不发出真实交易。配置传输、认证和命令确认方式见 [架构文档](mt5-server-ui-architecture.md)，最终实现需结合 SDK 和部署环境选择。

必须验证以下事项：

- SDK 与目标 Build、编译工具链、位数及 ABI 的兼容性，插件入口和卸载机制。
- 回调内容、线程限制、重复或乱序事件、历史补查和一致快照能力。
- 为指定目标账户创建交易及关闭指定 Hedging 仓位的支持范围；记录修改接口不能替代正常交易执行路径。
- 目标账户组、品种、交易权限、保证金及网关条件；同 Live 不代表所有条件相同。
- 实际交易路径以及桥接、Dealer、其他插件的行为；不承诺同价、同时成交或固定毫秒延迟。
- 净值样本可用时点、源分批成交、Close By、SL/TP、强平和人工操作的可识别性。
- 执行意图与真实订单/成交的可靠关联；超时或崩溃不代表失败，未核对前不能重发。
- 事件回调仅做 SDK 允许的工作，不能假设任意线程可以调用接口。

DLL 之外的管理界面关闭不应停止 DLL 的跟单执行；此为架构目标，需部署测试。插件停用或卸载不默认平掉客户仓位；停止执行后界面应明确显示同步已停止。

## 8. 后续验收要求

1. 多源多目标、同一目标接收多个源时，关系、配置、仓位和失败状态互不混淆。
2. 每条关系三种开仓模式分别计算正确；净值模式在跟单提交前取样并记录双方查询时间及源成交时间，后续净值变化不再调整已有仓位。
3. 重复事件和开仓分批成交不导致重复固定手数交易。
4. 每条关系旧仓排除、新仓纳入、启用前挂单启用后成交、暂停后恢复均符合第 6 节。
5. 三种模式的部分平仓均基于本次比例与目标实际余量；连续减仓、人工部分平仓和最终平仓不超量。
6. 目标手动全部平仓后映射终止，之后源事件不补仓或操作该仓位。
7. 目标端不存在由插件复制的挂单和 SL/TP；源 SL/TP 触发平仓仍同步关闭结果。
8. 自跟随、重复关系、关系图循环和双执行者被阻止；同账户不同来源仓位不会误平。
9. 无效净值、品种不可交易、保证金不足、部分成交或结果未知均提供可追溯状态。
10. 提交前后崩溃、重载、界面重连、配置变更及卸载能够核对真实状态，不盲目重发。

这些是实现后的验收目标。SDK 无关计算或模拟通过，仅证明所测业务逻辑，不能代替 DLL 编译、服务器集成和测试账户交易验证。
