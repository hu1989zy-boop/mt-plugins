## 本轮范围

- 同一交易服务器、Hedging/USD、多对多关系，每条关系独立倍率、净值比例或固定手数。
- 每次启动建立当前源持仓基线、回调序号屏障和服务器时间截止点。源首次成交时间必须晚于截止点；边界上无法区分的交易忽略。日志出现 `READY` 后再产生测试新仓。
- 每个新源持仓先核对已结束的源开仓订单及全部实际入场成交。固定手数只计算一次；挂单本身不复制，挂单成交后的新持仓可以跟随。
- 目标用 Market Execution，优先 IOC，未允许 IOC 时选 FOK。一次只执行一个请求；可配置一个 `AllowedSymbol`，当前默认 `XAUUSDp`。
- 部分平仓按“目标实际剩余量 × 本次源平仓量 / 本次平仓前源剩余量”向下取整；源全平关闭映射目标的实际剩余量。
- 不设置目标 SL/TP；源 SL、TP、普通手动平仓的实际出场成交走相同关闭逻辑。目标人工部分关闭后用实际余量继续计算，人工全平后不补开。
- Close By、净持仓反转、展期换票、拆分、迁移、交易数据库修订不在本轮范围；遇到不支持的持仓历史进入核对状态。

## 1. Windows 构建

在 VS2022/v143 或 VS2026/v145 的 **x64 Native Tools Command Prompt** 中切到项目根目录：

```cmd
scripts\build-windows.cmd -Executor -SdkRoot "D:\SDK\MetaTrader5"
```

SDK 路径改成之前构建探针时的实际目录。该目录下 `Include\MT5APIServer.h` 必须是 **6182**；也可使用项目 `vendor\mt5-sdk`，此时省略 `-SdkRoot`。两个 Server API 目标不需要链接 SDK 的 Manager/Gateway DLL。

脚本会构建、跑三组测试、检查两个 DLL 的入口并生成 SHA256 清单。产物为：

```text
build-windows\package-executor\
  TradeCopierExecutor.dll
  TradeCopierSdkProbe.dll
  TradeCopierManager.exe
  TradeCopierJournal.exe
  build-manifest.json
  executor-demo-validation.md
```

`build-manifest.json` 的 `can_copy_trades` 为 true，`trading_enabled_by_default` 为 false；构建成功不会将 `mt5_executor_execution_verified` 改为 true。脚本本身不安装 DLL 或启动交易。

若旧构建缓存属于另一 VS 版本，使用新的构建目录，例如加 `-BuildDirectory build-windows-executor`。不要修改 SDK 的版本宏来消除编译错误。

例如将关系文件保存为 `D:\MT5Copier\copier.local.json`，并创建 `D:\MT5Copier\runtime` 目录。MT5 服务运行账户需要读取配置文件、读写 runtime 目录的权限。账本路径可设为 `D:\MT5Copier\runtime\executor.journal`，首次不存在时由插件创建。

原样例全部禁用。编辑器的“保存”仅写文件；由下面的 `ConfigPath` 应用，编辑器没有服务器实时发布或状态连接。

## 3. 新增执行器配置

将新 DLL 放到已验证的 Demo **交易服务器**插件目录，按原探针的发现模块流程新增 `TradeCopierExecutor` 配置。不是客户终端的 Experts 目录。

此次已确认安装目录为 `D:\MT5 Platform\Demo MainTrade`，DLL 位于其 `plugins\TradeCopier` 子目录。新模块在对应 Demo 交易服务重启后被发现；首次日志已确认 `server-id=1`。更换环境时仍需重新核对实际服务路径和日志中的 ID。

首次保留 `Armed=0` 启用，日志会报告实际 `server-id`、Build/API 和 `DISABLED`。然后停用，填写：

| 参数 | 类型 | 值/说明 |
| --- | --- | --- |
| `Armed` | Integer | 默认 0。其余参数确认后设 1，下一次启用才进入执行阶段 |
| `ExpectedServerId` | String | 此次 Demo 日志已确认 `1`；其他环境填其首次日志中的实际 server-id，不是账号或 Build 6182 |
| `ApiAppId` | Integer | 默认 3101；应为该服务器给本插件保留的应用 ID，允许 1–4095。字段 1–3 用于程序标记、意图 ID 和服务器 ID |
| `ConfigPath` | String | 实际关系 JSON 的绝对路径 |
| `JournalPath` | String | 固定本地磁盘账本绝对路径；不支持网络共享/可移动盘 |
| `AllowedSymbol` | String | 默认 `XAUUSDp`，大小写和后缀须与实际符号一致 |

执行器同时核对运行 API=6182、Build=6182、服务器 ID/类型、账户组所属服务器、Hedging/USD 以及实际组品种配置。它不根据服务器名称推断 Demo；本阶段请使用已经升级的 Demo 环境。

账户、路径或合约配置不符合时，日志会给出失败原因。不要把 `plugin successfully started` 单独当作交易就绪；需要看到 **`TradeCopierExecutor: READY`**。

配置只在启用时读取；改参数需停用再启用。**已有账本绑定原配置的规范化内容**：改变账号、关系、启用状态、手数参数、应用 ID 或品种时，不会静默迁移旧映射。当前没有配置迁移界面。

| 动作 | 必须核对的结果 |
| --- | --- |
| 启用前已有源仓 | `READY` 后不补开对应目标仓 |
| 源普通新开仓 | `PREPARED` → `QUEUED` → `CONFIRMED`；目标账号、方向、手数及对应 ticket 正确 |
| 源先关一部分，再关剩余 | 对同一个映射目标依次部分/全部关闭，不触碰其他持仓 |
| 源挂单成交，再触发 SL | 挂单阶段目标无挂单；成交后开仓，SL 实际出场后平仓 |
| 源触发 TP 平仓 | 对应目标持仓按实际剩余量关闭，不触碰其他仓位 |
| 目标手动部分减仓 | 后续源平仓按目标实际余量计算 |
| 目标手动全平 | 后续源事件不重新开仓 |
| 源一次开仓分为多笔成交 | 同一源持仓固定手数只产生一个额度 |
| 两个源跟到同一目标账户 | 各自目标 ticket 独立，关闭源 A 不影响源 B 的目标仓 |
| 有已确认映射时停用/启用，期间无源交易 | 核对原映射后继续，不产生重复开仓 |

`QUEUED` 仅表示请求已入队。只有订单历史、带相同 API 标记的成交量和精确持仓状态相符，才记录 `CONFIRMED`。目标仓位必须实际可见；仅看到探针日志不能算执行器验收通过。

### 已执行步骤：净值比例及冻结快照核对

用户于本轮提供当前 Equity：50001 为 `7896.46 USD`，50002 为 `10268.40 USD`。这些值用于规划测试手数；它们尚不是执行器提交时的冻结快照。管理界面选择“净值比例”，“净值系数”填 `1.00`，点击“更新 / 加入列表”并另存为 `D:\MT5Copier\copier.equity-100.local.json`。该操作只保存草稿。

## 5. 异常与重启处理

每个请求先写入追加账本并完成 `FlushFileBuffers`，再调用 `TradeRequest`。账本保存配置身份、启用基线、源/目标映射、已处理源平仓成交、请求与成交 ID、冻结数量和净值证据。每个记录带版本、连续序号和校验值；文件有独占写锁，同一 Windows 主机的同一服务器 ID 还受命名对象租约约束。

- **请求部分成交、结果未知或超过 30 秒未确认**：记录实际可见证据，停止新请求，不自动补足/重试。
- **崩溃后残留 Prepared/Submitted 请求**：重启保持 HALTED，避免把“尚未保存 Request ID”误当作未下单。本版尚未提供人工核对后的恢复命令。
- **停机期间源仓发生交易**：已知映射转 REVIEW，不回放遗漏的平仓；停机期间新仓不会补跟。
- **目标手动减少且源账本一致**：重启可保留映射并采用实际余量；目标增加、换票或不明消失需要核对。
- **落盘失败、文件损坏、队列满或 SDK 读取异常**：停止发出新请求。账本截断尾部也会拒绝启动，不静默丢弃可能已成交的意图。

遇到这些状态，先停用执行器，保留原账本与服务端历史供核对。**不要删除、截断账本或改换 JournalPath 来尝试重发**；它们可能记录了已经到达服务器的请求。当前没有自动平掉异常仓位的操作。

停用后可离线检查：

```cmd
TradeCopierJournal.exe "D:\MT5Copier\runtime\executor.journal"
```

检查器只读取已有账本；打印账户、ticket、数量（VolumeExt）、请求/成交状态和冻结净值，退出时不修改内容。它需要执行器已释放文件写锁。

阶段编号：`0 Candidate / 1 Opening / 2 Active / 3 Closing / 4 Closed / 5 ManualClosed / 6 Review`；意图编号：`0 Prepared / 1 Submitted / 2 Confirmed / 3 Rejected / 4 Review`。

## 当前工程限制

- 请求串行，后台正常轮询间隔 200 ms；回调可以唤醒线程。历史查询与快照账本偏向小规模 Demo 验证，未做高负载吞吐验收。
- 新源开仓超过 30 秒未处理会转 REVIEW；净值两次查询及提交前新鲜度上限 5 秒。
- 源订单结束前等待归并；若跟单提交前源已开始平仓，则不追赶该生命周期，记录 REVIEW。
- 10000 个映射、100000 个请求、单快照 16 MiB、账本 256 MiB 是停止阈值，不自动删历史或轮换文件。
- 没有多主机主备协调、自动重发、异常仓位自动修复、热更新或已存配置迁移。
- Windows DLL 编译、Demo 加载、多个独立批次的目标开平仓 CONFIRMED、人工全平 MANUAL_CLOSED、正常启停恢复及旧仓不补跟已有用户截图；净值冻结快照及该轮映射 Closed 已经账本输出核对，未成交挂单撤销已有源记录及目标无交易的用户确认。已通过场景及分批次请求计数见本文件验收状态。逐笔成交归档、人工全平后源继续关闭、其余数量取整边界、固定手数的源分笔成交归并、更复杂关系及异常恢复等仍需补充。单元测试没有连接账户。
