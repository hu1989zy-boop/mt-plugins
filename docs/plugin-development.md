# 插件开发流程

用于新插件、执行机制变更，以及影响交易、资金、路由或账户权限的功能。目标是留下可复核的业务和接口依据，同时持续推进开发。小范围修正只补受影响的部分；用户只要求界面时先完成界面，不据此宣称后台已可行。

## 1. 用具体例子确定需求

在目标插件维护一份分析文档，可使用 [分析模板](templates/plugin-analysis.md)。先从现有代码、README 和已确认的对话取得信息，避免让用户反复解释。

| 需要明确的内容 | 典型问题 |
| --- | --- |
| 操作对象 | 是改账户，还是某一笔订单/成交/持仓？组别只是筛选还是汇总计算？ |
| 生效时间 | 按请求前、预计成交后还是实际成交后的状态选规则？ |
| 新旧关系 | 已有仓位和历史数据要保持什么？是否允许追溯重算？ |
| 数量与边界 | 临界值等号属于哪一档？分段还是整笔？单位和小数精度？ |
| 规则冲突 | 优先级、排除条件、未命中、停用和修改规则如何处理？ |
| 失败行为 | 拒单、跳过、重试或暂停哪一部分？是否会影响平仓和其他账户？ |

至少写出正常例、临界例和反例。只有会改变结果且无法从上下文确定的选择才需要用户回答；技术实现选择由开发者调查解决，不能把查 SDK 的工作转交给用户。

## 2. 建立 MT4 / MT5 接口依据

两个平台分别记录目标 server build（未知则标明）、SDK 版本、位数、账户模式和适用品种计算模式。Server API、Manager API、Gateway、终端接口的能力不能互相假定。

从业务效果逆向找到字段、结构、读写接口和生命周期。针对关键机制记录：

- 字段含义、单位、原始值来源及是否会被服务器重新生成；与同名但含义不同字段的区别。
- 回调发生在验证、外部成交、数据库写入、账户重算的哪个阶段；参数是当前状态还是预计未来状态。
- 修改的是临时对象、真实记录还是全局设置；服务器何时采用该值，重启后从哪里恢复。
- 指针和数组谁分配释放、回调可用的 API、锁和重入限制、错误码及部分成功。

文档只确认字段定义时，记录“字段定义已确认”，不要扩大为“服务器行为已确认”。厂商产品存在可以作为可行性线索，不能替代对自己代码的验证。搜索应优先使用本机 SDK/附带文档和一手资料，不上传商业 SDK、真实账号数据或配置。

## 3. 验证最可能推翻方案的假设

优先验证一旦错误就会影响客户交易或迫使架构重写的假设。最小验证必须说明输入、预计结果、观测点，以及什么结果会否定该方案。

例如动态杠杆要分别验证：订单比率能否保存、预交易保证金检查是否采用它、实际账户保证金是否改变、旧仓是否保持原依据、重复回调是否累乘、部分平仓和重启是否丢失记录。不能只看到一个 setter 返回成功就认定全部成立。

记录结论时使用：

| 状态 | 必须提供的依据 |
| --- | --- |
| 已确认 | 确认范围、版本/配置和可重复的证据；例如只确认字段定义或只确认单元测试结果 |
| 待验证 | 明确假设、最小测试、预期与否定条件、缺少什么环境 |
| 当前条件不支持 | 具体限制及范围，已核对的替代机制；若只是没查到资料，仍记为待验证 |

没有真实服务器时可完成实现、构建入口、错误处理和模拟测试，将依赖实服的结论留待验证。根据实际未知项决定哪些执行入口需要保持禁用；不得仅因资料不完整就一概移除已验证的功能。调查以能支持下一步决策为止，不无限搜索，也不提前把问题推给供应商。

## 4. 实现时保护业务不变量

设计配置热更新、同账户并发和事件去重。明确唯一处理标识、原始值与已调整值的保存方式、元数据命名空间、失败后可否重试、部分写入如何恢复。禁止重复处理产生累乘、重复成交、重复收费或重复分配。

涉及交易执行时，预交易检查与最终成交/记账要采用一致的规则版本和计算依据。明确检查后持仓或配置变化时如何重新验证或协调状态；外部已经成交时，应按平台生命周期处理落账和恢复，不能简单拒绝本地写入而遗留内外不一致。

按实际功能检查相关生命周期：部分成交/平仓、挂单激活、CloseBy、净持仓加仓或反转、外部网关已成交、迁组、规则停用、断连、启动恢复和日终。非本次支持范围应明确列出，不暗中用简化实现处理。

对回调耗时、SDK 请求次数、锁范围、队列上限、扫描规模和重试限流给出依据。事件驱动、后台线程和休盘调度都需要负载验收，不能保证天然不影响交易。部署前还应明确与其他插件修改同一对象/字段时的所有权和兼容约束。

## 5. 审查与交付

关键变更安排独立审查，给审查者业务不变量和接口证据，重点寻找能推翻实现的情况，而不仅是格式问题。主代理核对发现后修复并做相关回归；多个代理意见一致不替代真实证据。

交付状态按实际完成层次填写，不要求每个文案修改都跑全部测试：

| 层次 | 可以证明什么 | 不能替代什么 |
| --- | --- | --- |
| 规则/模拟测试 | 输入边界、业务算法、错误处理和所建模型 | 真实 SDK 行为 |
| Windows 原生编译 | 指定 SDK/架构下的编译和链接 | 服务器运行 |
| DLL 加载与导出检查 | 模块和入口可加载 | 回调、成交和保证金效果 |
| Demo 场景 | 记录的服务器版本与配置下的实际行为 | 未覆盖配置和负载 |
| 负载与恢复验收 | 测得规模下的延迟、竞争和恢复表现 | 所有生产环境 |

分析文档、README 和交付说明保持一致。明确哪些功能未实现、哪些只是未验证，附运行命令和复现数据来源。探针与原型可以阶段性交付，但原任务未完成的部分要继续记录，不能用“需要测试”掩盖还没接入的代码。

## 本次动态杠杆问题留下的约束

已知本地 SDK 包含 MT4 `TradeRecord.margin_rate`，以及 MT5 订单/持仓 `RateMargin()`。不能因为注释写“换算率”就排除它参与逐仓保证金调节的可能；也不能反过来认定所有计算模式都能按相同倍数调整。当前证据和未完成项以 [动态杠杆分析](../plugins/dynamic-leverage/docs/new-position-leverage.md) 为准，后续应维护该文档而非复制未经验证的结论。

## 后续任务如何使用

本仓库根目录的 [AGENTS.md](../AGENTS.md) 是项目指令入口。Codex 按项目目录链读取这类指令；新任务应在本项目中启动，已有任务若尚未读取新文件，需要显式读取它。其他仓库不会自动继承本仓库文件。[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

用户可简短要求：“按本仓库 AGENTS.md 开发这个插件，先给出业务口径、SDK 证据和关键验证方案，再持续实现；区分未实现与未验证。”这用于确认本次任务的工作方式，不需要逐条重新描述规范，也不要求用户每阶段批准。
