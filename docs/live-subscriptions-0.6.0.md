# 0.6.0：按映射隔离故障，订阅实时加入与退出

本版替代 0.5.x 的全局 HALTED 和按账户隔离策略。DLL、管理 EXE 和账本检查器必须一起更新。管理协议为 v2，账本 schema 为 6；支持读取旧账本，升级写入后不能用旧程序读取或覆盖。

## 源码包 r1：Windows 构建脚本修复（2026-09-21）

原 0.6.0 源码包的 `scripts/build-windows.ps1` 在同一个构建清单中重复声明 `management_protocol_version`，分别赋值为 2 和 1，触发 PowerShell 的 `DuplicateKeyInHashLiteral`，编译尚未开始。r1 删除旧值 1，保留与管理客户端、服务端一致的协议版本 2，并将构建脚本修订号更新为 20。

已解压旧源码的用户只需替换这个脚本，构建命令及 `-SdkRoot` 路径不变。运行代码和交易策略没有变化。已静态核查脚本的哈希表字段无重复、协议版本一致；本次未在 Windows PowerShell / MSVC 上执行完整构建。

## 行为

| 事件 | 处理 | 其他订阅 |
| --- | --- | --- |
| 保证金不足且明确零成交 | 跳过该次开仓，记录拒单，不补单 | 继续开平仓 |
| 部分成交、请求超时、提交异常、身份不一致 | 只将相关映射置为待核对，不盲目重发 | 包括同账户的其他映射，继续开平仓 |
| 单一品种、净值或源历史读取错误 | 只影响对应映射 | 继续运行 |
| 子账户被强平 | 经持仓/成交历史核实后更新剩余量；全平则结束映射，不补开原仓 | 继续运行；该账户下一笔新信号仍可尝试 |
| 回调队列溢出或无效回调 | 报告事件丢失，继续消费后续回调 | 已有映射仍通过历史查证平仓 |
| 在管容量或空间预留不足 | 跳过无法容纳的新仓，不设置全局暂停 | 已接受的映射继续管理 |
| 运行时账本写入/压缩失败 | 显示存储降级，停止新增没有持久化保证的仓位；可核实的已有仓位在内存中继续管理和平仓 | 不进入全局 HALTED |

操作员主动点击“暂停新仓跟随”的含义不变：暂停新仓，已有仓位继续管理。交易异常不会替操作员设置这个状态。旧账本中的 HALT 转为诊断，未知请求仍保留待核对，绝不因移除 HALT 而重发。

### 加入与修改

在“常规”页添加并启用关系，直接点击“应用配置”，无需先全局暂停，也无需把其他订阅平仓。

- 新关系有独立的时间与回调序号边界，只跟生效后的新仓。旧源仓的后续分笔成交也不会补跟。
- 未修改关系保留原边界：配置提交时已经排队的新仓回调仍正常处理。
- 修改手数方式、参数或品种规则只作用于之后的新仓；已有映射保留开仓时的规则与目标品种。
- 配置提交检查“原生效配置是否仍相同”，不会因为交易导致账本版本不断增长而无法提交。多个管理端修改同一配置时，后提交的过期草稿会被拒绝。

### 退出

删除或停用某条关系后应用配置，即请求退出。确认框列出将退出并平仓的源账号、跟单账号和关系 ID。

1. 停止接收该关系的新仓，取消尚未提交的候选开仓。
2. 对已确认的仓位，使用账本中的账号、仓位票号、方向、目标品种和实际剩余量逐笔平仓。
3. 已提交但尚未确认的开仓，等确认后再平仓。
4. 曾超时或提交结果不明的请求，退出期间有界查询成交历史；只有完整成交与目标仓位都核实后，才继续退出平仓。查证不等于重发。
5. 与源历史读取有关的待核对映射，若没有未决交易且目标归属明确，退出可直接核实并平掉目标仓，不依赖源账号仍可读取。

运行页显示“退出中”数量与对应映射。成功平仓后按现有规则回收映射；无法核实、部分成交、无法交易等情况仍显示退出中/待核对及原因，不会提前报告已退出。

同一跟单账户的其他订阅、人工仓位不属于本次退出范围。停用全局配置或清空全部关系，是明确请求所有关系退出并关闭其跟单仓位，确认框会说明。关闭管理窗口不触发退出。

## 存储和故障边界

- 账本保留在管和未决证据，已结束记录仍按既有规则清理；10,000 条映射、32 MiB 单快照、64 MiB 检查点阈值不变。
- 存储正常时，开仓和平仓均先写入准备记录，再提交 SDK。
- 存储故障后，为避免停止已确认仓位的平仓，允许这些平仓在内存中推进；这段进度没有持久化保证，程序再次崩溃或断电后必须以服务器证据核对，不能把旧账本当作最新实盘状态。此时不允许提交订阅配置，也不新增仓位。
- 损坏、丢失或无法读取的账本不能推断仓位归属；启动仍会报告加载失败，不会清空文件后假装恢复。MT5 停服、机器断电、SDK 不可用也不能保证交易成交。这里移除的是软件运行中主动全局终止其他健康映射的机制。
- 关系隔离保证不会因为一个订阅失败而主动暂停或取消其他订阅；各关系仍共享 MT5 API、工作线程和磁盘，不能承诺配置提交或批量退出带来零毫秒调度开销。

- 第 10 个账户：700 次开仓和 700 次平仓；中途加入不补仓。

另有真实文件容量回归：10,000 条映射、1,000 次新增开仓、1,000 次部分平仓、10,000 次最终平仓全部完成，检查点及重启重放通过。峰值主文件 66,901,074 字节，小于 64 MiB（67,108,864 字节）阈值。

本机 ASan/UBSan：4/4 测试组通过，其中执行测试 59,412 项检查、管理 UI 调度测试 137 项检查。Windows EXE 交叉构建及 SDK 6182 兼容语法检查通过。

这项模拟用于验证调度、归属、去重和数量正确性；不是 MT5 服务器延迟测量。验证记录随源码包的独立验证包提供。本机 ASan/UBSan 测试、Windows 交叉编译和 Server API 6182 兼容语法检查不替代 Windows 原生 MSVC 测试及 Demo 验收。

## Windows 构建与升级

在已配置 SDK 的源码目录，以 x64 Native Tools 命令行执行：

```bat
scripts\build-windows.cmd -Executor -BuildDirectory build-windows-0.6.0
```

SDK 不在默认目录时，按构建脚本参数提供 `-SdkRoot`，不要复用旧源码目录中的 DLL。构建脚本会运行 Windows 原生单元测试；全部通过后再部署。

升级时停止插件并保留完整运行目录备份，包括主 journal 与其 sidecar 文件；替换 DLL、管理 EXE 和检查器后重新启用，不删除仍有在管或未决仓位的账本。新启动日志应含 `MANAGEMENT v2`、`no automatic global halt` 和 `(0.6.0)`。如果源仓在插件停用期间发生变化，相关旧映射会待核对，不会盲目补交易。

Demo 验收建议按以下次序执行：

1. 三个账户正常跟随时，让其中一个保证金不足；检查其拒单不影响另外两个继续开平仓。
2. 50004 随时加入，只跟新源仓；50002、50003 原有仓位及后续新仓保持正常。
3. 50004 有持仓时退出，核对其本关系仓位清零；源仓、人工仓及其他关系仓位保留。
4. 在快速开仓时退出，核对在途开仓确认后也被关闭，退出中数量最终为零。
5. 对单个子账户制造强平，其他账户仍正常跟随源平仓；被强平仓位不补开。
6. 最后复跑 30 单/秒、1,000 个源仓、持仓 10 秒并中途加入/退出的服务端压测，提供完整源账号、跟单账号和执行器日志核对真实延迟。
