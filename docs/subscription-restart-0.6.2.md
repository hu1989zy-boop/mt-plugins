## 原因

每次插件启动都会创建新的事件队列，回调序号重新从 1 开始。运行中加入订阅时，执行器会保存加入时的队列序号，防止已经排队的旧信号被新订阅补跟。

旧代码将这个序号保存进 journal，重启时只更新全局启动门槛，没有更新每条订阅的门槛。例如前两个账号的门槛为 0，第三个账号后来加入时的门槛为 20,000；重启后的第一笔新信号序号为 1，只能通过前两个账号的检查。第三个账号甚至还没进入品种匹配和请求生成，所以不会出现它的拒单日志。

该问题来自 0.6.0 的运行中加入功能，0.6.1 仍受影响。此前重启测试使用了持续递增的模拟序号，没有覆盖真实队列重建后的序号归零。

## 修复

- 启动时，将每条订阅的回调序号门槛重置为本次启动的队列水位。
- 保留订阅加入时间、关系 ID、账号、品种规则、手数规则、暂停状态及请求编号。旧仓继续按冻结的开仓规则管理。
- 全局启动时间、队列水位和已有仓位基线继续阻止补跟；启动后的实时加入仍使用独立的加入门槛。
- journal 校验仅允许在全局启动门槛变化时统一更新序号，不能借此移除订阅、改关系 ID、修改加入时间或只放宽某一条序号。
- 成功写入后记录 `RESTART rebased_subscription_sequences=... queue_watermark=...`。没有需要调整的序号时不输出该行。

源码版本 0.6.2，插件数字版本 120，构建脚本修订 22。管理协议仍为 v2，账本二进制 schema 仍为 6。512 个总在途请求、每账号 8 个和 10,000 条映射上限不变；本次不改变调度、品种匹配或交易拒单处理。

## 构建与验收

解压源码包后，在其中的 `mt-plugins` 目录运行：

```bat
scripts\build-windows.cmd -Executor -SdkRoot "D:\SDK\mt5-sdk" -BuildDirectory build-windows-0.6.2
```

脚本的全部 Windows 测试通过后，停止插件并关闭管理端，备份完整运行目录和 journal sidecar，再替换 DLL、管理 EXE 与账本检查器。保留现有 journal，重新启用插件。启动日志应包含 `(0.6.2)` 和 `subscription queue watermarks rebased on restart`。

旧版本的 journal 校验器不认识本次允许的门槛更新，不能假定可以用旧 DLL 或旧账本检查器直接读取升级后的增量记录。备份用于回溯，不能在发生新交易后直接覆盖当前账本。

Demo 验收：

1. 点击“读取生效配置”，核对 50001 → 50004 存在且启用，源掩码覆盖 `EURAUDp`，目标使用自动匹配；目标账号应唯一匹配可交易的 `EURAUDr`。
2. 若新仓处于暂停状态，按当前测试计划恢复。用新的源仓验证三个账号分别产生 `PREPARED`、`QUEUED`、`CONFIRMED`，源平仓后各自完整平仓。已错过或已平掉的旧源仓不补跟。
3. 在全部测试仓位结束后重启插件，再验证第一笔新仓仍能到达三个账号。
4. 单独测试第三个账号退出、再次加入及之后重启；原两个账号应持续正常，重新加入只跟新仓。

若 50004 仍没有请求，提供读取后的生效配置和新一轮启动至开平仓完整日志，继续区分关系过滤、目标品种和交易服务器拒单。
