# 0.4.3：不同跟单账号并行等待成交

> 0.6.0 已更新运行策略：按映射隔离异常，不自动全局终止；订阅可运行中加入，退出会关闭该关系仓位。新的行为及升级步骤以 [0.6.0 说明](live-subscriptions-0.6.0.md) 为准。

> 当前 0.5.1 的调度、增量账本格式及复跑说明见 [0.5.1 文档](throughput-0.5.1.md)。下文保留该历史版本的验证记录。


> 历史版本说明。0.4.5 已改为清理已结束记录和替换运行检查点，不再自动积累历史归档，并新增新仓容量保护。当前行为与升级步骤见 [运行账本与容量保护](live-state-journal.md)。

## 原来的延迟来源

0.4.2 及以前的执行器每轮最多提交一笔交易，任何一笔请求尚未确认时，其他订阅都不能提交。服务端工作线程每轮还有最长 200 ms 的轮询等待，跟单目标成交通常不会唤醒该线程。账号增加后，插件内的等待会逐个累加。

本版解除跨账号的全局等待，继续使用单个执行线程调用 SDK 和维护账本。一个账号的 `TradeRequest` 被接收后，即可提交下一账号的请求；多个账号可以同时等待 MT5 处理并回传结果。返回请求 ID 只表示进入服务器队列，界面仍在核对实际成交后才标为“已确认”。这与原始 SDK 的 `IMTServerAPI::TradeRequest` 入队语义一致。

## 调度规则

| 项目 | 0.4.3 行为 |
| --- | --- |
| 不同跟单账号 | 最多 32 个账号各有一笔请求等待成交；空位随独立确认释放 |
| 同一跟单账号 | 全部订阅共用一次一笔的限制，上一请求确认前不提交下一笔；同一仓位先确认开仓再平仓 |
| 平仓与新开仓 | 在有空位时优先处理已建立映射的平仓，再提交新开仓 |
| 单个账号回报慢 | 占用自己的一个空位，不阻止其他空位工作；结果可以乱序确认 |
| 超过 32 个账号 | 有界分批推进，轮转处理；没有新增无限队列或 SDK 多线程调用 |
| 拒绝 / 明确未提交 | 对应映射进入待核对，不重试该映射；其他可独立核对的映射继续 |
| 部分成交、未知结果、超时或 API 异常 | 保留停止新请求的保护；已经明确提交的其他请求继续核对，不自动重发 |
| 进程重启 | 所有未决请求进入待核对，不因批量提交而自动重发 |

本版 32 是源码中的在途上限，没有新增插件参数。单个跟单账号的多个仓位仍按一次一笔处理；实际成交速度还受 MT5 内部处理、账号组、磁盘和成交通道影响，不能保证全部账号在同一毫秒成交。

如果源仓在某个候选请求提交之前已经结束，或开仓排队超过原有有效期，仍按原保护停止该映射，不追开已经结束的交易。

## 同时减少的开销

- 一个源开仓对应多条订阅时，合并为一次映射写入。
- 一批请求先全部保存 Prepared 并完成同步刷盘，随后逐笔调用 SDK；提交结果合并再刷盘。正常一批最多 32 笔需要两次提交阶段快照，不再每笔各写两次。成交确认也合并写入。
- 同轮中相同源开仓事件的完整历史读数共用一份，并限制缓存数量；每轮重新读取，源和目标身份校验仍保留。净值模式的每个账号仍独立查询并保存净值，提交时仍检查快照时效。
- 调度只对未结束映射和在途请求发起 SDK 查询，不反复查询已关闭映射及已确认的历史请求。
- 源平仓及目标成交事件会唤醒工作线程，包括仍在管理的已删除订阅。唤醒使用代次检查，处理期间到达的通知不会在进入等待时丢失。
- 有在途请求时保留 50 ms 轮询兜底；无在途请求时保留 200 ms 兜底。这是两轮工作之间的等待上限，不是 API 调用、批次或端到端执行时间承诺。

## 持久化与故障边界

批量提交没有跳过“先落盘再交易”：整批 Prepared 完成同步写入之前，不会调用任何交易提交接口。提交途中发生不确定结果时立即停止发送剩余请求，明确尚未调用 SDK 的尾部标记为未提交。若进程在结果落盘前崩溃，已持久化的 Prepared 会使恢复进入待核对，不能自动重发。

某笔异常导致停止新请求后，其他已知已提交请求继续登记结果；这不代表解除 HALTED，也不会自动发送后续平仓。磁盘写入失败后无法继续可靠记账，保持停止并要求人工核对。

账本继续使用 schema 3；0.4.2 的“老仓保留开仓规则、新仓使用新配置”行为保留。可读取原 schema 1 / 2 / 3 账本，保留原文件；从旧格式首次升级写入 schema 3 后，0.4.1 及更早程序不能读取。

**0.4.3 尚未实现账本归档或压缩。** 2026-09-17 现场已触及 256 MiB 文件上限并停止平仓；0.4.4 的修复见 [账本轮换](journal-rotation.md)。该修复引入归档与检查点，但仍保存全量状态，不能据此宣称大历史账本延迟及总磁盘占用已经完全解决。

## 批次日志

增加 `BATCH` 行，例如字段：

```text
BATCH first_intent=1 prepared=32 queued=32 in_flight=32 planning_ms=... prepare_flush_ms=... dispatch_ms=... result_flush_ms=...
```

- `planning_ms`：本轮选择映射、源历史、账户 / 品种及数量检查的时间。
- `prepare_flush_ms`：整批 Prepared 快照编码、写入与同步刷盘时间。
- `dispatch_ms`：本批 SDK 提交及其逐笔日志的时间；不包含等待最终成交。
- `result_flush_ms`：提交结果快照编码、写入与同步刷盘时间。
- `queued`：返回明确入队结果的数量；`in_flight` 是当时仍待核对的已提交请求总数。

这些耗时来自单调时钟。结合每个 intent 的 `QUEUED` / `CONFIRMED` 日志判断实际排队及成交确认耗时，不把入队时间当作成交时间。

## 构建和更新

将 `mt5-trade-copier-0.4.3-account-pipeline-source.zip` 的 `mt-plugins` 内容合并到现有源码目录，保留自己的 Server API 6182 SDK。执行：

```cmd
cd /d "D:\work\mt-plugins"
scripts\build-windows.cmd -Executor -BuildDirectory build-windows-0.4.3
```

构建通过后，在 Demo 维护窗口暂停新仓、等待当前请求确认，记录现有映射，停用插件并等待 `plugin shutdown finished`。备份程序与账本后，从 `build-windows-0.4.3\package-executor` 更新 DLL、管理 EXE 和账本检查器：

- `TradeCopierExecutor.dll` → `D:\MT5 Platform\Demo MainTrade\plugins\TradeCopier\TradeCopierExecutor.dll`
- `TradeCopierManager.exe` / `TradeCopierJournal.exe` → `D:\MT5Copier`

**保留插件参数和 `D:\MT5Copier\runtime\executor-two-to-one.journal`，不清空账本。** 多实例共用 DLL 时需全部卸载后替换。启用管理通道的启动日志应包含 `account pipeline ready, max-inflight=32` 和版本 `0.4.3`。

无需为了本功能平掉老仓；卸载期间执行器无法管理交易，如果源仓期间变化，现有重启检查仍可能进入待核对。升级账户 / 规则快照的详细说明见 [0.4.2 文档](frozen-opening-rules.md)。

## 已有验证与 Demo 验收

自动化模拟覆盖：

- 100 个账号跟随同一源仓；首批 32 笔在任何确认之前发出，首批只调用两次提交阶段持久化和一次源历史读取。
- 首个账号持续等待，其余 99 个仍可发出；乱序确认释放空位，后续正常全部平仓，票号与数量逐笔对应。
- 多源同目标账号保持一次一笔；该账号的平仓优先于新开仓；其他账号可独立完成开平仓。
- 批次中间拒绝、未知返回、部分成交、抛异常、准备 / 结果刷盘失败，以及异常后继续登记已提交请求。
- 暂停时取消尚未发送的候选，已发送请求继续核对；保留旧仓管理、真实文件账本重放和重启不重发。
- 回调在工作期间及等待期间到达、轮询超时、停止唤醒。

100 账号测试包含刻意乱序回报；整个 100 开仓 + 100 平仓场景调用 `Store.Save` 28 次。该结果是调度与持久化次数测试，**不是 Windows 磁盘或真实服务器延迟测试**。

本地 ASan / UBSan 四组测试、Windows EXE 交叉编译及 API 6182 辅助语法检查的记录见 [构建验证](windows-build-validation.md)。Windows MSVC 构建、实际回调时序、账号组处理能力和端到端延迟仍待 Demo 验证。

建议先以现有两个账号测试：确认两条 `QUEUED` 能在首条 `CONFIRMED` 之前出现，开仓和平仓均测试；再在 Demo 分别使用 10、32、超过 32 个测试账号，记录首末入队间隔、各笔成交确认延迟、批次四项耗时和未决请求数量。对比时使用插件自己的 `QUEUED` / `CONFIRMED` 行，并先确认没有其他未决请求占用测试账号；同时核对目标票号、量和请求数。
