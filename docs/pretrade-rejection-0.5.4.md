# 0.5.4：识别保证金不足的交易前拒单，保持已有仓位平仓

> 后续 [0.5.5](routine-no-money-0.5.5.md) 补上了明确零成交开仓拒单的自动回收，避免其长期占用待核对记录、阻挡恢复/配置或积累到容量阈值。下文描述 0.5.4 当时的行为。

## 补充日志确认的原因

2026-09-18 的 50003 日志（补充附件 f315fc6e）包含 415 条 PREPARED、407 条成功成交 / 订单执行和 8 条 `not enough money`。

- 固定手数为每笔 EURAUDp 0.02 手，成功开仓 407 笔。
- 第一笔资金不足前：Equity 9,358.29，Margin 9,340.89，FreeMargin 17.40。
- 后续拒单前：Equity 9,358.04，Margin 9,340.89，FreeMargin 17.15。
- 下一笔订单校验后的 Margin 为 9,363.84，较原值增加 22.95；FreeMargin 将为 -5.55 / -5.80，所以服务器拒绝新开仓。这是日志中的预检查结果，不代表这些失败订单实际成交。
- 请求 9325、9328、9331、9334、9337、9340、9343、9346 均属于 50003，均为 0.02 手开仓。
- PREPARED 时间为 13:40:38.712–38.840，HALTED 为 13:41:08.768–08.868，相隔 30.014–30.056 秒，与代码中的 30 秒确认窗口吻合。

已确认的故障链：**保证金不足拒单 → 插件遗漏交易前拒单回报 → 只查订单 / 成交历史，一直等待 → 30 秒后当作结果不明 → 旧版全局 HALTED → 停止其他已有仓位的后续平仓。**

SDK 6182 的 `IMTTradeSink::OnTradeRequestRefuse` 明确提供交易前校验拒绝事件；`IMTRequest` 提供 ResultRetcode、ResultDeal、ResultOrder、ResultVolumeExt。旧适配器只订阅成功成交路径，`deal == nullptr` 时直接忽略，因此漏掉了此类无成交回报。10019 在 SDK 中定义为 `MT_RET_REQUEST_NO_MONEY`。

日志关联统计与各请求的时间、行号见 `out/analysis/no-money-20260918/summary.json`。订单号和成交号没有直接携带 intent，毫秒内交错行不能被用作任意逐行配对；本结论结合了同账号同手数拒单、8 笔请求身份及后续超时集合。

## 与 0.5.3 的区别

0.5.3 隔离结果不明确的目标账号，允许其他账号已确认仓位继续平仓。明确的资金不足拒单不应被当成未知成交，否则不足资金的账号本身也会停止平仓。

0.5.4 在 0.5.3 基础上补上明确拒单证据：

1. 捕获本执行器的交易前拒单回调，并兼容请求处理回调中的同类结果；无需存在 deal。
2. 请求调用 SDK 前登记 intent，支持回调在 `TradeRequest` 返回之前到达。
3. 工作线程验证 intent 标记、服务器标记、账号、请求 ID、品种、方向、手数、开平仓标志、目标票号，并要求明确 10019 且结果成交量 / 订单号 / 成交号为零。
4. 证据匹配才记录为 `Rejected`；不必等 30 秒，不重发该请求，不触发账号不确定隔离或全局 HALTED。
5. **包括保证金不足账号在内，所有已确认仓位仍按原冻结规则跟随平仓。** 原有并发额度和准确目标票号校验保留。
6. 新增 `REJECTED intent=... target=... operation=... request=... retcode=10019 reason=server_pretrade_no_money_zero_fill` 日志。

该通道只接受本次验证过的明确保证金不足拒单。超时、连接异常、结果字段矛盾或不匹配仍保持原有未知结果保护，不把无历史记录本身当成拒单证据。

## 有界内存与落盘顺序

- 回调只复制借用对象的字段，使用容量 4,096 的固定队列，不在回调中查询 SDK、写账本或分配事件内存。队列溢出进入既有 callback fault 保护。
- 只保留已登记在途 intent 的证据，最多 128 项；重复回调幂等处理，矛盾回调保持不确定。
- **先持久化确认 / 拒单结果，再释放该请求的回调证据。** 落盘失败不释放证据、不继续交易。
- 已结算的迟到回调不会重新建立缓存。只读查看已拒绝记录明确标注“账本记录，非本次服务器查询”。
- 账本仍为 schema 5 / delta frame 4，没有清空或改变现有文件格式。

失败请求继续保留可核对记录，仍受原有待核对记录的配置 / 恢复限制；本版没有引入拒单记录的自动清理或事故账本恢复功能。

## 当前事故与部署

本地源码已经修正；**没有直接操作 Demo 账号或替换服务器程序，也不会凭文本日志修改当前 journal 的交易状态**。现场已有 HALTED、遗留仓位与历史待核对记录不会因升级自动消失，不应删除账本绕过保护。

保留当前日志和账本副本，完成现场仓位核对后，在维护窗口构建和更新。使用现有 Server API 6182 SDK，源码包不附带 SDK：

```cmd
scripts\build-windows.cmd -Executor -BuildDirectory build-windows-0.5.4
```

输出 `build-windows-0.5.4\package-executor`，同步更新执行器、管理程序、账本检查器。启动能力日志包含 `pretrade no-money refusal callback enabled` 和 `0.5.4`。

## 验证场景

新增自动化验证覆盖：同步拒单回调、重复和矛盾回调、账号 / 请求 / 品种 / 方向 / 数量 / 票号不匹配、非零成交证据、超时代码不能冒充拒单、队列满、持续拒单缓存回收、落盘失败不提前丢失证据。

核心场景：10 个跟单账号，保留已有持仓后让其中一个账号的后续 8 笔开仓返回 10019；等待超过 30 秒，再批量关闭信号源。验证该账号原有仓位和其他 9 个账号的全部实际仓位都能平仓，8 笔失败请求没有重发或误判为成交，真实账本重放一致。

大规模场景命令：

```cmd
build-windows-0.5.4\Release\tradecopier_execution_tests.exe --no-money-soak
```

该测试使用 1,000 个源仓、10 个跟单账号、8 笔明确拒单，预期 9,992 次开仓成交与 9,992 次平仓成交，所有实际仓位归零。成交和时间为模拟，账本实际落盘；不代表 MT5 实际端到端延迟。

## 本地验证结果（2026-09-18）

- ASan / UBSan 四组回归全部通过；执行器 55,543 项检查，管理界面调度 115 项检查。
- 1,000 源仓 × 10 跟单账号模拟通过：10,000 笔开仓请求中，8 笔明确保证金不足拒单，9,992 笔开仓成功，随后 9,992 笔平仓成功。包括保证金不足账号原有 992 笔仓位在内，所有实际仓位归零。8 笔失败请求保留核对记录，没有重发，也没有触发 30 秒误停。
- 真实账本完整重放一致，回调证据在结果落盘后释放；失败落盘时不释放证据。
- 大规模测试程序运行 177,308 ms，包含模拟、实际账本写入和大量断言；这不是 MT5 跟单延迟。
- Windows 管理程序、检查器和测试程序交叉构建通过；Server API 6182 语法检查通过。
- 尚未执行 Windows MSVC 本机测试和 Demo 部署；需现场确认实际 `OnTradeRequestRefuse` 回调字段，并复测“明确资金不足拒单后，关闭源仓，原有目标仓位照常关闭”。若字段不一致会保留未知结果保护，不会放宽身份或成交量校验。

原始测试结果位于 `out/validation-0.5.4`。对照源码差异位于 `changes-from-0.5.3.patch`，源码包不包含 SDK、运行账本或用户日志原文。
