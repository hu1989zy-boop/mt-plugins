# 0.6.1：300 个订阅的调度优化与延迟验证

> 目录调整：当前 MT5 实现位于 `plugins/trade-copier/mt5/`。本文保留对应版本的源码包和现场路径；在当前仓库复跑命令、查找产物时，请按 [目录与构建入口](../README.md#目录与构建入口) 执行。

## 结论

拓扑：10 个信号源，300 个跟单账户，每个账户只跟一个源，每源 30 个。

本机模拟中，下表四种负载的所有开平仓均核对一致，没有漏单、重复单、串账号或残留仓位，观察到的最大模拟成交延迟均小于 1 秒。**这不是实际 MT5 的延迟承诺，也不能保证任意负载下每单都在 1 秒内成交。**

| 场景 | 跟单开仓 / 平仓数量 | 开仓 P99 / 最大值 | 平仓 P99 / 最大值 | 峰值映射 |
| --- | ---: | ---: | ---: | ---: |
| 每源每秒 1 单，每源 20 单，持仓 10 秒 | 6,000 / 6,000 | 93 / 189 ms | 200 / 200 ms | 3,300 |
| 每源每秒 3 单，每源 50 单，持仓 10 秒 | 15,000 / 15,000 | 182 / 239 ms | 388 / 388 ms | 9,300 |
| 每源先开 10 单，合计 3,000 个跟单仓位同时触发平仓 | 3,000 / 3,000 | 69 / 69 ms | 471 / 471 ms | 3,000 |
| 每源每秒 1 单，每次源历史/目标持仓读取额外等待至少 100 微秒 | 4,500 / 4,500 | 77 / 77 ms | 826 / 895 ms | 3,300 |

合计 28,500 次跟单开仓、28,500 次平仓。P99 表示 99% 的样本不超过该值，最大值单独列出；四场景超过 1,000 ms 的样本数均为 0。账本精确重放、重启后没有重发请求均通过。

### 测试条件与边界

- macOS arm64，Apple Clang 17，Release 优化，真实单写者 FileJournal 与同步磁盘写入；每次 Save/Prune 另加 5 ms 等待。
- 源事件按真实经过的时间发送，10 个源同步产生事件，模拟成交固定在请求提交后 20 ms；工作循环每轮等待 10 ms，回调每轮最多处理 32 条。
- 延迟起点：源开仓/平仓事件的计划发生时间；终点：模拟目标成交时间。另存提交时间和执行器确认时间，可分别分析排队、提交和确认。
- 没有连接 MT5，也没有真实报价、网络、桥接、保证金和交易服务器排队。这些因素会改变真实延迟。读取延迟场景只给源历史及目标持仓查询增加开销，不代表所有 SDK 调用。
- 测试是有限时长样本，不是长期服务等级承诺。实际验收还应统计 P95/P99/最大值、超时比例和逐笔数量，不能仅看平均延迟。
- 账户数不能单独决定延迟。10 个源均每秒 30 单、每源跟 30 个账户、持仓 10 秒，将需要约 90,000 条同时在管映射和每秒 9,000 次开仓；稳定阶段还叠加约 9,000 次平仓。本版的 10,000 条容量不能覆盖这个场景。

## 修改内容

1. **最小手数跳过不再残留“待核对”。** 仅在尚未生成交易请求、开仓手数低于目标最小量时跳过并回收。服务器日志保留 `SKIPPED ... reason=skip_below_minimum`，不会补单、向上凑手数或阻塞其他订阅。
2. **安全清理旧记录。** 启动时，只有精确原因 `skip_below_minimum`、没有任何请求、没有目标仓位/余量/已处理平仓、且源初始量与剩余量一致的旧 Review 才回收。任意 Prepared/Submitted/Confirmed/Rejected/Review 请求、部分成交或不确定记录都会保留。保留暂停状态、订阅配置和请求 ID；无需删除整个 journal。
3. **源平仓回调直接提示调度。** 回调只复制信息，工作线程优先检查该源仓的在管映射；仍必须从服务器历史与目标持仓核实后才能提交平仓。重复、过期或错误提示不能直接产生交易。未收到提示时仍有周期扫描。
4. **已发现的平仓优先处理同源订阅。** 避免扫描游标跨过某个订阅后，让它再等完整一轮。繁忙账号只等待自己的名额，其他账号继续。队列去重、有界，并在已结束记录回收后重映射索引；保留扫描预算以发现其他平仓。
5. **总在途请求上限 128 → 512，每账号仍为 8。** 减少大规模订阅被拆成很多批次和反复写盘的开销。这是请求数量上限，不是账户数量限制，也不是 512 个线程。请求超时、拒单和异常仍按映射隔离。
6. **优化账本整数编码。** 由逐字节追加改为一次追加 8 字节，预分配常见快照大小。保持原有小端编码、校验、先持久化再提交、账本 schema 6、管理协议 v2、32 MiB 快照上限和 64 MiB 检查点阈值。

源码版本 0.6.1，执行器插件数字版本 119，构建脚本修订 21。原有运行中加入/退出、旧仓冻结规则、保证金不足隔离和不自动全局 HALT 的行为继续保留。

## 回归证据

- Release 与 ASan/UBSan 均通过核心、配置、执行和 UI 调度测试；执行回归覆盖同源平仓优先、回调提示去重/核实、旧记录迁移和失败恢复。
- 用修改前的执行器代码运行平仓优先测试可复现失败，修改后通过。
- 10,050 轮最小手数跳过：不产生目标请求、不累积 Review；另一健康订阅的 20,100 次开平仓完整完成。
- 10,000 条映射容量测试：1,000 次新增开仓、1,000 次部分平仓与 10,000 次最终平仓通过，检查点及恢复通过。峰值主文件 66,921,697 字节，低于 64 MiB 阈值。
- 10 个跟单账户的实时加入/退出逻辑时钟测试通过；它验证数量和归属，不作为延迟测量。
- 优化前后同一个 10,000 映射编码样本均为 4,691,939 字节，SHA-256 完全一致；100 次编码本机耗时从 965 ms 降至 242 ms。该小基准只测编码，不含完整写盘和 SDK。
- Windows 管理 EXE 交叉链接、Server API 6182 兼容语法检查通过；**尚未执行 Windows 原生 MSVC 测试及 Demo 部署验证。**

验证包保留每笔 `trades.jsonl`、执行器日志、场景 `summary.json`、独立核对脚本与报告。`final-*` 是最终版本的结果；`scale-*`、`journal-*` 是开发过程中的对照，包含曾经超时和触及容量保护的失败场景，不应当成最终版结果。早期 3 Hz 场景曾少跟 3,300 个目标开仓，已接受的仓位全部平掉；最终版同负载全部 15,000 个目标开仓和平仓核对通过。

## Windows 构建与升级

解压到新目录，进入其中的 `mt-plugins`，在 x64 Native Tools 命令行运行：

```bat
scripts\build-windows.cmd -Executor -SdkRoot "D:\SDK\mt5-sdk" -BuildDirectory build-windows-0.6.1
```

将 `-SdkRoot` 改为实际 SDK 根目录，须包含 `Include\MT5APIServer.h`。构建脚本运行原生测试，全部通过后再部署生成的包。

升级前备份完整运行目录（含 journal 和 sidecar），停止插件并关闭管理端，同步替换 DLL、管理 EXE 和账本检查器，再启用插件。不删除仍有在管或未决仓位的 journal。启动日志应含 `(0.6.1)`、`max-inflight=512` 和 `source close callbacks and sibling priority enabled`；满足清理条件时还会出现 `MIGRATION cleared_unsubmitted_minimum_reviews=...`。

升级保留操作员原来的新仓暂停状态。源仓在停用期间变化的旧映射仍需要核对，不能用这次优化替代事故恢复。

## 复现模拟与现场验收

下面命令只运行本地假交易端口、写入指定的新测试目录，不向 MT5 下单。输出目录必须不存在：

```bat
build-windows-0.6.1\Release\tradecopier_stress_simulation.exe sim-300-1hz 5 20 10 30 1 20 10000 0 0
build-windows-0.6.1\Release\tradecopier_stress_simulation.exe sim-300-3hz 5 20 10 30 3 50 10000 0 0
build-windows-0.6.1\Release\tradecopier_stress_simulation.exe sim-300-bulk 5 20 10 30 1 10 10000 0 1
build-windows-0.6.1\Release\tradecopier_stress_simulation.exe sim-300-read 5 20 10 30 1 15 10000 100 0
```

参数顺序：目录、额外写盘等待 ms、模拟成交等待 ms、源账号数、每源跟单账户数、每源每秒开仓数、每源开仓总数、持仓 ms、读取等待微秒、是否集中平仓。

Demo 验收按 1 Hz → 3 Hz → 集中平仓的顺序复测，保持总映射不超过 10,000。检查每个源及每个目标账号的开平仓数量、手数、源与目标仓位归属、最终持仓、未决请求及超 1 秒的比例。另测保证金不足、子账户强平、持仓时加入/退出与部分平仓。只有真实服务器在约定负载、硬件和异常条件下的日志通过后，才有依据确定服务延迟目标。
