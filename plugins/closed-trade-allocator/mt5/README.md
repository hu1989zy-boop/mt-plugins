# MT5 平仓订单概率分配 Server API 插件

独立 DLL：`ClosedTradeAllocatorMT5.dll`。不依赖跟单插件的内部库，不执行目标账号的市价开平仓。

首版处理同一交易服务器、同币种的 Hedging 账号 A → B。来源交易必须恰好具有一笔 `ENTRY_IN`、一笔等量 `ENTRY_OUT`，两个关联历史订单均已成交，并且源持仓已经消失。分批平仓、加仓、反转、Close By、拆分成交和独立关联费用记录跳过并保存原因。日结/月结佣金的来源组不参与分配；首版只冻结成交上已经归属的利润、佣金、Swap 和 Fee。

开仓/平仓两笔历史订单、两笔成交分别复制其原始 SL、TP、成交量、价格、时间及费用。初始 SL/TP 与平仓时 SL/TP 可以不同，零值也原样保留。所有目标订单及成交的 `Comment` 均为空。源账号和源历史不修改。

## 构建

Windows x64、Visual Studio C++ 工具链、CMake 3.21+、有合法授权的 MT5 Server API SDK。SDK 不重新分发。

```powershell
./scripts/build-windows.ps1 -SdkRoot C:/SDK/mt5-sdk
```

或：

```powershell
cmake -S plugins/closed-trade-allocator/mt5 -B build/allocator-mt5 -A x64 -DMT5_SDK_ROOT=C:/SDK/mt5-sdk -DCLOSEDALLOC_MT5_BUILD_SERVER=ON
cmake --build build/allocator-mt5 --config Release --parallel
ctest --test-dir build/allocator-mt5 -C Release --output-on-failure
```

产物为 `build/allocator-mt5/Release/ClosedTradeAllocatorMT5.dll`。本地接口以 SDK 6182 为准，`MTServerCreate` 要求 API 版本一致。macOS/Linux 配置只构建共享核心与 MT5 快照/交易边界测试，不产生 Windows DLL。

## Administrator 参数

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `SourceLogin` | `0` | 必填，来源 A |
| `TargetLogin` | `0` | 必填，接收 B，与 A 不同 |
| `LossPercent` | `30` | 净亏损单独立入选概率，百分数 0～100 |
| `ProfitPercent` | `70` | 净盈利单独立入选概率，百分数 0～100 |
| `Enabled` | `1` | 0 暂停新写入；暂停区间按服务端时间记入账本 |
| `Armed` | `0` | 0 仅筛选/核对；1 才允许历史及余额写入 |
| `PollSeconds` | `30` | 未写入/读取失败后的重试间隔，1～3600 秒；运行时至少 5 秒，不再控制正常成交发现速度 |
| `SettleSeconds` | `5` | 平仓年龄和源快照稳定窗口并行等待，1～86400 秒；至少两次一致读取，不能证明延迟佣金已归属 |
| `RescanSeconds` | `300` | 增量补扫周期，60～86400 秒；旧配置缺少该参数时自动用 300 |
| `JournalPath` | `C:\ClosedTradeAllocator\allocator-mt5.journal` | 独立持久化账本，必须为服务器固定本机盘绝对路径 |

参数通常每 5 秒读取一次，后台退避时会延后；概率变化仅影响未决定的源交易。首次启用时间在首次创建账本时冻结。使用账号 + PositionID 查询该持仓从时间 0 到当前的完整成交集合，覆盖“启用前开仓、启用后平仓”；启用前已平仓的交易不处理。服务器标识取 `About().server_id`。运行时不可更换账号关系或账本路径。

同一来源快照必须至少被读取两次，并持续不变达到 `SettleSeconds`，改变后重新等待；提交之前再次读取源开平订单/成交、该 PositionID 完整成交集合以及当前源持仓，并重查来源 Hedging/即时佣金条件。任何新增/缺失关联成交都会阻止旧快照写入。源 SL/TP 或费用修订不会获得新的抽样身份。账本路径拒绝相对路径、UNC 和网络盘，防止工作目录切换和网络刷盘语义改变。

单次源 dataset 查询及源待检查队列最多 100,000 条；查询明确设置行数限制且拒绝部分结果。补扫时间片发生超限会缩小时间片，不能丢掉剩余记录继续写入。目标历史订单和目标历史成交仍分别限制 100,000 条，提交前为两订单和两成交预留容量。目标历史与余额完整核对仍有随历史增长的成本。

B 必须是专用接收账号，设置 `USER_RIGHT_READONLY` 或 `USER_RIGHT_TRADE_DISABLED`，不得存在持仓或挂单，不得有人工/其他插件并发交易、资金或历史修改。全局命名 mutex 按服务器和 B 账号排斥另一插件实例，包括使用不同账本的实例。该 mutex 不会阻止人工和其他软件；历史核对会检测它们的变化。

## 事件处理与负载边界

成交与历史订单新增/修改/删除事件触发检查。回调只筛选源账号、复制必要标识、写固定容量 4096 的无锁队列并合并唤醒，不查询数据库、不写账本、不修改交易；纯开仓新增事件不触发查询。同一个 PositionID 合并处理。所有 SDK 对象只在所属回调或后台线程使用。

后台线程采用低于普通线程的优先级，至少间隔 1 秒调度一次，公平轮转三个阶段：最多 8 个源持仓检查、最多 1 次提交和 1 次只读恢复、一个补扫时间片。源检查批次有 100ms 软预算；单个已进入的 SDK 调用/历史写入不能中途强制取消。成功写入之间至少 5 秒，失败按 `PollSeconds`（最低 5 秒）退避。单轮超过 100ms 后冷却至少 5 秒，超过 1 秒后冷却至少 30 秒。

正常事件路径只读取指定 PositionID 的完整成交集合及相关订单，不再按秒拉取全部源成交。首次订阅后的补扫从账本启用边界开始，以最多 1 小时时间片补查；后续每 `RescanSeconds` 从上次成功游标前 60 秒补查。重启从持久启用边界恢复；事件队列满/同步异常会暂停新提交，并重新补查，直到补查完成。关闭事件可能先于持仓消失，此时最多以 5 秒间隔再查三次，避免部分平仓持仓持续忙轮询。

启动和重新补查时还会分批核验账本中已有的源 PositionID，以发现整套源历史已删除的情况；分段补扫和这些核验都结束后才恢复新提交。源历史缺失、修订或持仓重新出现时，保留原冻结快照、抽样与目标回执并进入待核对，阻止该关系继续写入。

`SettleSeconds=5` 时，正常新平仓单需至少 5 秒稳定窗口，再加后台排队、查询、写入和界面刷新耗时；这不是固定到账时限。旧插件已有参数不会被 DLL 默认值覆盖，升级后需手动将原 `SettleSeconds=30` 改为 5。源事件缺失、启动补查、大量待写、慢调用退避都会延后。

每分钟 `ClosedTradeAllocator load:` 记录待检查数、源查询/补扫累计次数、事件溢出累计次数、该分钟最大处理耗时及当前冷却时间。普通统计附带实际 `Enabled/Armed` 和一条待写/待核对原因；TSV 仅在内容改变时落盘。

这些措施限制插件工作量，但无法保证对共享 Trade Server 零影响。尤其目标完整历史核对、`TradeBalanceCheck` 以及单个源 dataset 查询依然消耗服务器资源，软预算不能限制单次调用的内部耗时。正常客户交易延迟及服务器 CPU/I/O 必须用 Demo 负载对照验证，不以本地测试通过代替验收。

## SDK 写入和资金语义

仓库内授权 SDK 文档已明确：

- `Docs/html/imtserverapi_historyadd.htm`：`HistoryAdd` 向历史库新增已结束订单，零票号由服务器分配。
- `Docs/html/imtserverapi_dealadd.htm`：`DealAdd` 直接增加历史成交，**不会修改账户余额和持仓**。
- `Docs/html/imtserverapi_tradebalancecheck.htm`：`TradeBalanceCheck(login, 0, ...)` 只读核对账户余额与完整成交历史；`fixflag=1` 按完整成交历史校正账户余额/信用。
- `Docs/html/imtserverapi_dealperform.htm`：`DealPerform` 会实际开平持仓、按组计算佣金和利润，因此本插件不调用。

流程：

1. 核对来源快照、目标币种/合约、专用账号状态及完整目标历史；要求目标账面余额/信用与历史已经一致。
2. 冻结余额、净值、可用保证金、信用以及其他目标历史的 SHA-256 摘要；每次外部写入前先持久化步骤意图。
3. `HistoryAdd` 开仓订单，读取服务器票号后 `HistoryUpdate` 关联新 PositionID；再写入平仓订单及开平两笔 `DealAdd`。目标票号均由服务器产生，源票号仅用于独立来源标记。
4. 回查全部字段及关联，确认没有目标持仓/挂单；确认其他目标历史完全未变、账面余额仍是原值，且历史余额只多出该笔净盈亏。
5. 持久化余额步骤意图后，**只调用一次** `TradeBalanceCheck(..., 1, ...)`。再用 `fixflag=0` 与账户资金读取核对余额、信用、净值、可用保证金及完整历史。

不额外生成余额成交，否则原交易利润和余额成交会在报表中重复计入。`TradeBalanceCheck` 扫描整个目标账号历史，有成本；不适合在持仓/历史繁忙账号上运行。历史写入与资金应用不是事务：其中一步失败会留下已写入部分，账本保留待核对，后续写入受共享核心隔离，插件不自动回滚。

## 幂等和恢复

API 内部字段应用 ID `0xCA5`，槽位 1～7 分别为版本 magic、持久化随机任务 tag、记录角色、源账号、源 PositionID、源票号及实际写入时间。请在服务器插件间保留该应用 ID。目标 `Comment` 不承载标记。提交前同时检查源账号 + PositionID，检测到不同 tag 的已有分配时进入待核对，防止换账本后再次入账。

写入前日志必须成功落盘。重启后只根据冻结快照、API 标记、票号、历史摘要和资金证据做只读核对。部分历史、回执丢失、资金校正结果未知、来源修订或额外目标活动均不得触发补写或再次资金校正。只有明确“尚未进入任何外部调用步骤且无目标标记”的任务，才可继续原抽样决定。不要删除账本来清理异常任务。

`<JournalPath>.tsv` 内容变化时原子更新，包含选择结果、概率、抽样值、目标标识和最后结果；故障也记录到 Server 日志。账本写失败或未预期异常使工作线程停止，需修复后重启。SDK 在 Stop 前自动移除订阅，插件关闭回调入口，结束工作线程并等已有回调退出后释放资源；Start 失败时主动回滚订阅。

Server 日志在统计发生变化时输出盈利/亏损各自候选数、入选数、实际入选率，以及跳过、待写入、写入中、已完成、待核对总数；零候选的入选率显示 `n/a`。入选数与已完成写入数分开计算。

## 验证范围

本地可移植测试覆盖完整成交对、开平费用归集、SL/TP 独立保留、快照严格序列化、部分平仓/反转/Close By 排除和损坏数据拒绝。Windows DLL 构建及指定 MT5 Demo 服务器实测必须分别执行，不能用这些本地测试代替。

Demo 验证至少包括：两类概率 0/100；成本使毛盈利转为净亏损；SL/TP 非零、变更和零值；源历史原样；目标两订单两成交无备注；资金净变化恰好一次；无目标持仓；写入每一步中断/回执丢失后的只读恢复；资金校正前已有余额差异或并发历史变化时停止；服务端报表和持仓一致性检查；冻结规则与重启。未连接或写入真实服务器。
